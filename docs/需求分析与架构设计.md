## 第一部分：需求分析

### 1. 背景与目标

- **目标**：在 iPhone 上快速记录日常收支，按月查看花销结构和趋势，控制预算。
- **形态**：PWA（渐进式网页应用）。在 Safari 中打开后「添加到主屏幕」，全屏启动，体验接近原生 App。
- **约束**
  - 开发环境为 Windows，不依赖 Mac / Xcode / Apple 开发者账号。
  - 仅个人使用：不做注册登录、多用户、权限体系，也不需要上架审核。
  - 数据优先存放在手机本地，可离线使用；数据安全靠「定期导出备份」兜底。

### 2. 用户与使用场景

只有一个用户（我自己），典型场景：

| 场景 | 描述 | 关键诉求 |
|---|---|---|
| 随手记 | 付款后马上掏出手机记一笔 | **3 秒内完成**：打开即可输入金额，点分类，保存 |
| 补记 | 晚上回忆当天漏记的账 | 可改日期、时间 |
| 月度回顾 | 月底看花了多少、花在哪 | 分类占比、日趋势、与上月对比 |
| 预算控制 | 月中看还剩多少可花 | 月度总预算、分类预算、超支提醒 |
| 查账 | 找某一笔消费 | 按备注/分类/金额/时间筛选 |
| 备份迁移 | 换手机或清理 Safari 数据前 | 一键导出 / 导入 |

### 3. 功能需求

优先级：**P0** 首版必须；**P1** 第二版；**P2** 有空再做。

#### 3.1 记账（P0）

- 新增一笔：类型（支出 / 收入 / 转账）、金额、分类、账户、日期时间、备注。
- 自定义数字键盘，支持简单算式（如 `12.5+8`）。
- 默认值：日期取当前时间，账户取上一次用的账户。
- 编辑、删除（删除需二次确认）。
- 转账：从账户 A 转到账户 B，不计入收支统计。

#### 3.2 分类管理（P0）

- 预置常用分类：餐饮、交通、购物、居住、娱乐、医疗、学习、人情、其他；收入预置：工资、奖金、理财、其他。
- 支持新增、改名、改图标/颜色、排序、隐藏（已有流水的分类不可物理删除，只能隐藏）。
- P1：二级分类（如 餐饮 → 早餐 / 午餐 / 晚餐 / 零食）。

#### 3.3 账户管理（P1）

- 账户类型：现金、储蓄卡、信用卡、微信、支付宝、其他。
- 每个账户有初始余额，余额 = 初始余额 + 流水汇总，实时计算。
- 首版可只用一个默认账户，界面上不强制选择。

#### 3.4 流水列表（P0）

- 按日分组倒序展示，每组显示当日支出/收入合计。
- 顶部切换月份，显示本月支出、收入、结余。
- P1：筛选（类型、分类、账户、金额区间）与关键字搜索备注。

#### 3.5 统计报表（P0 / P1）

- P0：本月分类支出饼图（或环形图）+ 排行列表；本月每日支出柱状图。
- P1：近 12 个月收支趋势折线；与上月同期对比；年度汇总。

#### 3.6 预算（P1）

- 月度总预算 + 可选的分类预算。
- 首页显示剩余预算和进度条；超过 80% 变黄，超过 100% 变红。

#### 3.7 数据备份（P0）

- 导出 JSON（完整备份，可还原）。
- 导出 CSV（便于用 Excel 分析）。
- 从 JSON 导入：支持「覆盖」与「合并（按 id 去重）」两种方式。
- 距上次备份超过 N 天（默认 14 天）在首页提示。

#### 3.8 其他（P2）

- 周期账单（房租、订阅自动生成）。
- 标签（如「出差」「旅行」，跨分类统计）。
- 应用锁（PIN 码）。
- 深色模式跟随系统（基础样式 P0 即可支持）。
- 多设备同步（见架构部分 §8 扩展）。

### 4. 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 冷启动到可输入 < 1.5 s；1 万条流水下列表滚动流畅，月度统计 < 300 ms |
| 离线 | 首次加载后完全离线可用，所有功能不依赖网络 |
| 数据安全 | 数据仅存本机；不接入任何第三方统计/广告 SDK；金额用「分」为单位的整数存储，避免浮点误差 |
| 可靠性 | 写入使用 IndexedDB 事务；导入失败整体回滚 |
| 适配 | iPhone 竖屏为主；适配刘海屏/底部安全区；支持深色模式 |
| 可维护性 | TypeScript；业务逻辑与界面分离；核心计算有单元测试 |

### 5. iOS 上 PWA 的已知限制与对策

| 限制 | 影响 | 对策 |
|---|---|---|
| 必须 HTTPS 才能启用 Service Worker | 本地 `http://192.168.x.x` 无法离线 | 部署到免费静态托管（Cloudflare Pages / GitHub Pages / Vercel），自带 HTTPS |
| Safari 存储可能被系统清理 | 极端情况下数据丢失 | 从主屏幕启动的 PWA 不受 Safari 7 天清理规则约束；启动时调用 `navigator.storage.persist()`；**定期导出备份是硬性要求** |
| 主屏 PWA 与 Safari 标签页的存储相互隔离 | 在 Safari 里打开看不到数据 | 只从主屏图标进入；文档中注明 |
| 无法使用 Face ID、桌面小组件、Siri | 体验略逊原生 | 用 PIN 码代替（P2）；可用「快捷指令」打开带参数的 URL 实现快速记账（P2） |
| Web Push 需 iOS 16.4+ 且需服务端 | 本地提醒做不了 | 预算/备份提醒改为打开 App 时的页内提示 |

### 6. 不做的事（Non-goals）

- 不做账号体系、多用户、家庭共享。
- 不对接银行、微信、支付宝账单自动导入（P2 可考虑解析其导出的 CSV）。
- 不做投资理财、资产估值。
- 不上架任何应用商店。

## 第二部分：架构设计

### 1. 总体架构

纯前端、本地优先（Local-first），没有后端服务。

```
┌──────────────────────── iPhone（主屏幕 PWA，standalone 模式）────────────────────────┐
│                                                                                    │
│  ┌──────────── 视图层 Views（Vue 组件）────────────┐                                  │
│  │  首页/流水   记一笔   统计   预算   设置/备份       │                                  │
│  └───────────────────────┬──────────────────────────┘                                  │
│                          │                                                           │
│  ┌──────────── 状态层 Stores（Pinia）──────────────┐                                  │
│  │  当前月份、筛选条件、设置项、界面状态               │                                  │
│  └───────────────────────┬──────────────────────────┘                                  │
│                          │                                                           │
│  ┌──────────── 领域服务 Services（纯 TS）───────────┐                                  │
│  │  TransactionService  StatsService  BudgetService │                                  │
│  │  BackupService       AccountService               │                                  │
│  └───────────────────────┬──────────────────────────┘                                  │
│                          │                                                           │
│  ┌──────────── 数据访问 Repository（Dexie）─────────┐                                  │
│  │  IndexedDB：transactions / categories / accounts │                                  │
│  │            budgets / settings                    │                                  │
│  └──────────────────────────────────────────────────┘                                  │
│                                                                                    │
│  Service Worker（Workbox）：缓存 HTML/JS/CSS/图标，离线启动                              │
└────────────────────────────────────────────────────────────────────────────────────┘
            ▲  首次访问 / 版本更新时拉取静态文件
            │
   静态托管（Cloudflare Pages 或 GitHub Pages，HTTPS）  ← 只放代码，不存任何账目数据
```

要点：

- **托管只承载静态代码**，账目数据永远只在手机的 IndexedDB 中，网站本身是公开 URL 也不会泄露数据。
- 分层依赖单向向下：视图 → 状态 → 服务 → 仓储。服务层是纯 TypeScript，不依赖 Vue，方便单元测试。

### 2. 技术选型

| 关注点 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript | 金额、日期等逻辑需要类型约束 |
| 框架 | Vue 3（`<script setup>`） | 上手快、生态全、中文资料多 |
| 构建 | Vite | 快，`vite-plugin-pwa` 一行接入 PWA |
| UI 组件 | Vant 4 | 移动端组件库，自带数字键盘、日期选择、滑动删除、安全区适配 |
| 状态管理 | Pinia | Vue 官方推荐 |
| 路由 | Vue Router（hash 模式） | hash 模式免去静态托管的路由回退配置 |
| 本地数据库 | IndexedDB + Dexie.js | 支持索引、事务、版本迁移；`liveQuery` 让界面随数据自动刷新 |
| 图表 | ECharts（按需引入） | 饼图、柱状图、折线图齐全，体积可控 |
| 日期 | dayjs | 轻量 |
| 离线 | vite-plugin-pwa（Workbox） | 自动生成 manifest 与 Service Worker |
| 测试 | Vitest + fake-indexeddb | 服务层与仓储层单测 |
| 部署 | Cloudflare Pages（或 GitHub Pages） | 免费、HTTPS、推送 Git 即自动发布 |

> 也可以换成 React + Ant Design Mobile，架构不变，只是视图层换掉。

### 3. 数据模型

所有金额以 **分（整数）** 存储；所有主键使用 UUID（便于将来合并导入、多端同步）；时间用毫秒时间戳。

```ts
// 流水
interface Transaction {
  id: string;              // UUID
  type: 'expense' | 'income' | 'transfer';
  amount: number;          // 分，恒为正数，方向由 type 决定
  categoryId?: string;     // 转账时为空
  accountId: string;       // 支出/收入的账户；转账时为转出账户
  toAccountId?: string;    // 仅转账
  occurredAt: number;      // 发生时间
  note?: string;
  tags?: string[];         // P2
  createdAt: number;
  updatedAt: number;
  deleted?: boolean;       // 软删除，为将来同步预留
}

// 分类
interface Category {
  id: string;
  type: 'expense' | 'income';
  name: string;
  icon: string;            // 图标名或 emoji
  color: string;
  parentId?: string;       // P1 二级分类
  sort: number;
  hidden: boolean;
}

// 账户
interface Account {
  id: string;
  name: string;
  kind: 'cash' | 'debit' | 'credit' | 'wechat' | 'alipay' | 'other';
  initialBalance: number;  // 分
  sort: number;
  hidden: boolean;
}

// 预算：month 为 'YYYY-MM'；categoryId 为空表示总预算
interface Budget {
  id: string;
  month: string;
  categoryId?: string;
  amount: number;          // 分
}

// 设置：键值对
interface Setting {
  key: string;             // 如 'lastBackupAt' | 'defaultAccountId' | 'currency'
  value: unknown;
}
```

Dexie 表与索引定义：

```ts
db.version(1).stores({
  transactions: 'id, occurredAt, [type+occurredAt], categoryId, accountId, updatedAt',
  categories:   'id, type, sort',
  accounts:     'id, sort',
  budgets:      'id, month, [month+categoryId]',
  settings:     'key',
});
```

- `occurredAt` 索引支撑按月范围查询（`between(monthStart, monthEnd)`），这是最高频的查询。
- `[type+occurredAt]` 复合索引支撑「本月支出」这类统计。
- 后续字段变更通过 `db.version(n).upgrade(...)` 做迁移，不丢数据。

### 4. 核心模块设计

#### 4.1 TransactionService

- `add / update / remove(软删除) / listByMonth(month, filter)`
- 校验：金额 > 0；转账时 `accountId ≠ toAccountId`；收支必须有分类。
- 写入同时更新 `updatedAt`。

#### 4.2 StatsService

统计全部基于「当月流水」在内存中聚合（单月通常几百条，无需预计算）：

- `monthlySummary(month)` → 支出、收入、结余
- `byCategory(month, type)` → 分类金额与占比，按金额降序
- `daily(month)` → 每日支出数组
- `trend(lastNMonths)` → 每月收支（P1，数据量大时可按月缓存结果）
- 转账一律排除在收支统计之外。

#### 4.3 BudgetService

- `progress(month)` → 总预算与各分类预算的已用、剩余、百分比、状态（正常 / 预警 / 超支）。

#### 4.4 AccountService

- `balance(accountId)` = 初始余额 + 收入 − 支出 − 转出 + 转入，实时计算。

#### 4.5 BackupService

导出 JSON 格式：

```json
{
  "app": "my-ledger",
  "schemaVersion": 1,
  "exportedAt": 1793059200000,
  "data": {
    "transactions": [], "categories": [], "accounts": [], "budgets": [], "settings": []
  }
}
```

- **导出**：生成 Blob → 通过 `navigator.share({ files })` 调起 iOS 分享面板，可存到「文件」/ iCloud Drive / 发给自己；不支持时回退为 `<a download>`。
- **导入**：`<input type="file">` 读取 → 校验 `app` 和 `schemaVersion`（旧版本先走迁移函数）→ 在一个 Dexie 事务中写入（覆盖模式先清空；合并模式按 `id` 比较 `updatedAt` 取新者）→ 任何一步失败整体回滚。
- 成功导出后写入 `settings.lastBackupAt`，供首页备份提醒使用。
- CSV 导出：`日期,类型,分类,账户,金额(元),备注`，加 UTF-8 BOM 防止 Excel 乱码。

### 5. 页面与路由

底部 Tab 栏 4 个入口，中间悬浮「＋」按钮：

| 路由 | 页面 | 内容 |
|---|---|---|
| `#/` | 首页 / 流水 | 月份切换、月度汇总卡片、预算进度、按日分组流水 |
| `#/add`、`#/edit/:id` | 记一笔 | 类型切换、分类宫格、金额键盘、账户/日期/备注 |
| `#/stats` | 统计 | 分类环形图 + 排行、每日柱状图、趋势（P1） |
| `#/budget` | 预算 | 设置与查看预算（P1） |
| `#/settings` | 设置 | 分类管理、账户管理、导入导出、关于/版本 |

「记一笔」交互目标：打开 → 分类宫格 + 键盘同时可见 → 点分类 → 输入金额 → 点「完成」，3 步完成。

### 6. PWA 配置要点

- `manifest.webmanifest`：`display: "standalone"`、`start_url: "./"`、主题色、180×180 `apple-touch-icon`。
- `index.html` 中添加：
  - `<meta name="apple-mobile-web-app-capable" content="yes">`
  - `<meta name="apple-mobile-web-app-status-bar-style" content="default">`（内容从状态栏下方开始，避免被遮挡）
  - `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">`
- CSS 使用 `env(safe-area-inset-*)` 适配刘海与 Home 指示条。
- Service Worker 采用 `registerType: 'prompt'`：检测到新版本时提示「有更新，点击刷新」，避免记账中途页面被强制刷新。
- 启动时调用 `navigator.storage.persist()` 申请持久化存储。

### 8. 开发、部署与安装流程

1. **开发**（Windows）：`npm run dev -- --host`，手机与电脑同一 Wi‑Fi，用 iPhone Safari 访问电脑 IP 调界面（此时无离线能力，属正常）。
2. **部署**：代码推送到 GitHub 私有仓库 → Cloudflare Pages 绑定仓库，构建命令 `npm run build`，输出目录 `dist`，每次推送自动发布并提供 HTTPS 域名。
3. **安装**：iPhone Safari 打开该域名 → 分享 → 「添加到主屏幕」。之后只从主屏图标启动。
4. **更新**：推送新代码后，下次打开 App 会提示更新，点击即可。数据不受影响。

> 隐私补充：URL 是公开的，但别人打开只会得到一个空账本，看不到你的数据。若仍介意，可在 Cloudflare Pages 前加 Cloudflare Access（免费，邮箱验证码访问）。

| v1.1（P1） | 账户、预算、筛选搜索、12 个月趋势、二级分类 |

### 10. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 本地数据被系统清理或误删 PWA | 高 | 持久化存储申请 + 备份提醒 + 导出到 iCloud Drive |
| iOS 版本更新改变 PWA 行为 | 中 | 只用标准 Web API；备份格式稳定且带版本号 |
| 浮点金额误差 | 中 | 全程整数「分」，只在显示时格式化 |
| 数据结构变更导致旧备份不可导入 | 低 | `schemaVersion` + 迁移函数，有单元测试覆盖 |

## 第三部分：v1.1 云端同步与登录

### 1. 变更背景

| 问题 | v1.0 的做法 | v1.1 的做法 |
|---|---|---|
| 网址公开，任何人都能打开 | 无 | 服务端登录校验，未登录拿不到页面和数据 |
| 数据只在一台手机，删 App 即丢失 | 定期手动导出备份 | 云端 D1 为主数据，登录即恢复 |
| 多设备（手机 / 电脑）数据不通 | 手动导出导入 | 自动双向同步 |

### 2. 需求变更

#### 2.1 登录（P0）

- 单一账号，**不开放注册**；账号由本人在电脑上运行脚本创建。
- 用户名 + 密码登录；登录后 90 天内免登录（每次使用自动续期）。
- 未登录时访问任何页面都跳转到登录页；数据接口返回 401。正式地址与所有预览地址同样受保护。
- 防暴力破解：同一 IP 或同一用户名连续失败 5 次，锁定 15 分钟。
- 「账号与同步」页：查看已登录设备、移除某台设备、修改密码（修改后其他设备下线）、退出登录。
- 退出登录或会话失效时，清除本机缓存的数据和离线文件。

#### 2.2 同步（P0）

- 记账照常先写本机，离线可用；联网后自动与云端同步。
- 触发时机：打开 App、本地有修改（2 秒防抖）、App 回到前台、网络恢复、每 5 分钟。
- 冲突规则：同一条记录以修改时间较新的为准（Last-Write-Wins）。
- 显示同步状态：上次同步时间、待同步条数、失败原因；支持手动「立即同步」。
- 首次登录时，本机已有数据自动上传合并。

#### 2.3 已有功能的调整

| 功能 | 调整 |
|---|---|
| 首页备份提醒 | 改为「同步提醒」：有未同步数据且超过 24 小时未成功同步时提示 |
| 清空所有数据 | 改为「清空所有流水」：将全部流水标记删除并同步到云端；分类保留 |
| 导入备份（覆盖） | 改为：本机现有流水全部标记删除，再写入备份内容，结果同步到云端 |
| 导出 JSON / CSV | 保留，作为额外保险 |
| 局域网 http 访问 | 不再支持（登录 Cookie 需要 HTTPS） |

#### 2.4 第二步（P1，本次不做）

- Face ID 登录（Passkey / WebAuthn），密码作为备用。

### 3. 架构

```
┌──────────────── iPhone / 电脑浏览器 ────────────────┐
│  Vue 视图 → Pinia → 领域服务 → Dexie(IndexedDB)       │
│                         │  写入时自动标记 dirty         │
│                    SyncService（push → pull）         │
│  Service Worker：离线缓存静态文件                      │
└──────────────────────────┬─────────────────────────┘
                           │ HTTPS + Cookie(__Host-sid)
┌──────────────── Cloudflare Pages ──────────────────┐
│  functions/_middleware.ts   所有请求先校验会话          │
│     ├─ 未登录：页面 → 302 /login；接口 → 401          │
│     └─ 已登录：放行静态文件 / 接口                      │
│  functions/api/auth/*       登录、退出、设备、改密码     │
│  functions/api/sync/*       push / pull              │
│  静态文件 dist/                                       │
└──────────────────────────┬─────────────────────────┘
                           │ D1 binding: DB
┌──────────────── Cloudflare D1（SQLite）────────────┐
│  users · sessions · login_attempts · records        │
└────────────────────────────────────────────────────┘
```

要点：

- **本地优先**：界面只读写 IndexedDB，响应快、离线可用；同步在后台进行，失败不影响记账。
- **服务端是主数据**：本机缓存可随时清除，登录后从云端完整拉回。
- **统一记录表**：云端用一张 `records` 表存放流水、分类、账户、预算（JSON 存储 + 元数据列），新增实体类型无需改表。
- **增量同步**：每次写入云端分配递增版本号 `rev`，客户端只拉取 `rev` 大于本地游标的记录，不依赖设备时钟。

### 4. 技术选型（新增）

| 关注点 | 选择 | 理由 |
|---|---|---|
| 服务端 | Cloudflare Pages Functions | 与静态站点同一项目、同一域名，随 `npm run deploy` 一起发布 |
| 数据库 | Cloudflare D1 | 免费额度充足（5 GB / 每日 500 万次读），Pages 原生绑定 |
| 密码哈希 | PBKDF2-SHA256（Web Crypto），10 万次迭代，随机盐 | Workers 原生支持，无需第三方库 |
| 会话 | 随机 32 字节令牌，Cookie `__Host-sid`（HttpOnly / Secure / SameSite=Lax），库中只存 SHA-256 | 可吊销、可列出设备；库泄露也拿不到可用令牌 |
| 建表 | `wrangler d1 migrations` | 版本化管理表结构 |

### 5. 安全设计

| 威胁 | 对策 |
|---|---|
| 陌生人访问网址 | 中间件拦截所有请求，未登录只能看到登录页 |
| 暴力猜密码 | 失败计数存 D1，5 次锁 15 分钟；用户不存在时同样计算哈希，避免据响应时间判断用户名 |
| 会话令牌泄露 | HttpOnly 防脚本读取；库中只存哈希；可在设备列表中移除；改密码使其他会话失效 |
| CSRF | SameSite=Lax + 写接口要求 `Content-Type: application/json` 且校验 `Origin` |
| 数据库泄露 | 密码只存加盐哈希；会话只存令牌哈希 |
| 拿到已解锁手机打开 App | 本步不处理（离线缓存仍可打开），第二步用 Face ID 解决 |

### 6. 风险与对策（新增）

| 风险 | 对策 |
|---|---|
| Workers 免费版 CPU 时间限制（10 ms）与 PBKDF2 计算量 | 迭代次数存在哈希串中，可调；上线后实测登录，如超限则降低迭代次数重设密码 |
| 同步冲突导致改动被覆盖 | 以修改时间为准，单人使用冲突极少；流水删除为软删除，可追溯 |
| 多设备时钟不一致 | 拉取用服务端 `rev` 游标；仅冲突判定使用客户端时间 |
| 退出登录时有未同步数据 | 退出前先同步；仍有未同步数据时二次确认 |

## 第四部分：v1.2 用户、角色与权限

### 1. 背景

v1.1 只有一个账号，账号靠命令行脚本创建。现在需要给家人等其他人开账号，并能在页面上自己管理账号和权限。

### 2. 需求

#### 2.1 数据范围

- **每个用户一本独立账本**：只能看到、修改自己的流水和分类，和 v1.1 一样。
- 权限决定的是：每个用户能进哪些页面、能用哪些功能。

#### 2.2 权限清单（固定在代码中）

| 权限 | 名称 | 控制的页面 / 功能 |
|---|---|---|
| `ledger.view` | 查看明细 | 首页明细 |
| `ledger.edit` | 记账 | 记一笔、编辑、删除（勾选时自动带上「查看明细」） |
| `stats.view` | 查看统计 | 统计页 |
| `category.manage` | 分类管理 | 分类管理页 |
| `backup.export` | 导出备份 | 备份页的导出功能 |
| `backup.import` | 导入备份 / 清空流水 | 备份页的导入功能、设置页的「清空所有流水」（需同时有「记账」权限） |
| `admin.users` | 用户管理 | 用户管理页 |
| `admin.roles` | 角色与权限 | 角色管理页 |

「设置」「账号与同步」（改自己的密码、查看设备、退出登录）对所有人开放。

#### 2.3 角色

- 预置两个角色，不能删除：
  - **管理员**：拥有全部权限（含今后新增的权限），不能修改。
  - **普通成员**：查看明细、记账、查看统计、分类管理、导出备份，可修改。
- 管理员可以新建角色，勾选权限，修改或删除自定义角色。正在被用户使用的角色不能删除。
- 每个用户只有一个角色。

#### 2.4 用户管理（需要 `admin.users`）

- 用户列表：用户名、显示名、角色、状态、最近活动时间。
- 新建用户：用户名、显示名、初始密码、角色。
- 编辑：修改显示名、角色，停用 / 启用。
- 重置密码。
- 删除用户：同时删除该用户的云端账目，需输入用户名确认。
- 保护规则：
  - 不能停用、删除自己，也不能修改自己的角色。
  - 系统里至少要保留一个启用中的管理员。
  - 用户被停用、删除，或密码被重置时，他已登录的设备立即下线。
  - 角色或权限变更后立即生效，下次请求即按新权限执行。

#### 2.5 同一设备切换账号

- 本机记录数据属于哪个用户。启动时发现当前登录的用户和本机数据的主人不同，先清空本机数据，再从云端拉取。（解决 v1.1 里提到的串数据问题。）

### 3. 架构变更

```
D1 新增：roles（角色，permissions 存 JSON 数组）
users 新增：role_id、display_name、disabled
共享模块：shared/permissions.ts（权限清单、页面与权限的对应关系，前后端共用）

请求 → 中间件取会话（同时联表取得角色权限，停用用户的会话视为无效）
     → /api/admin/*：校验 admin.users / admin.roles
     → /api/sync/*：pull 需要 ledger.view 或 stats.view；push 按实体校验（流水、账户、预算需要 ledger.edit；分类需要 category.manage）
前端：路由守卫 + 菜单按权限显示；权限信息缓存在本机，离线时也能用
```

### 4. 安全边界

| 层 | 控制内容 |
|---|---|
| 服务端（强制） | 管理接口的权限；同步接口的读写权限；停用用户不能登录、会话立即失效；保护最后一个管理员；数据按用户隔离 |
| 前端（体验） | 菜单、按钮、页面入口按权限显示；直接输入网址访问无权限页面时跳回 |

> 每个人的账本是独立的。页面级权限（如分类管理、导出）主要控制的是本人能用哪些功能，不涉及别人的数据。跨用户的安全边界由服务端负责。

## 第五部分：v1.3 支付宝 / 微信账单导入

### 1. 背景与约束

- 目标：大部分消费在支付宝、微信里完成，希望不必逐笔手动记账。
- 约束：
  - 两家的开放接口只面向商户，**没有给个人查询消费记录的接口**。
  - 模拟登录、抓取账号数据违反用户协议，有封号风险，**不做**。
- 因此采用「本人从 App 导出账单文件 → 在记账应用中导入」的半自动方式，建议每月做一次。

### 2. 需求

#### 2.1 导入流程（P0）

1. 在支付宝 / 微信中申请导出「用于个人对账」的账单，到邮箱下载压缩包，用 App 内收到的密码解压。
2. 记账应用：设置 → 导入账单 → 选择文件。
3. 自动识别来源（支付宝 / 微信）和文件格式（CSV / Excel），解析出交易。
4. 预览：显示新增 N 条、重复 M 条、跳过 K 条（附跳过原因）；可以按「交易对方」批量调整分类。
5. 确认后一次性写入，随后自动同步到云端。

#### 2.2 规则

| 项 | 规则 |
|---|---|
| 去重 | 分四层（详见详细设计 §5）：① 用「来源 + 交易单号」生成固定 id，重复导入、账单时间重叠、在另一台设备上再导一次都不会重复，已删除的记录默认不恢复（预览中可勾选恢复）；② 微信退款与原交易冲抵，按实际花费记账；③ 重新导入时如果因为后来的退款导致金额变了，更新原记录；④ 与手动记过的账比对（金额相同、时间相差 30 分钟内），标为疑似重复，默认不导入 |
| 收支类型 | 按账单的「收/支」列：支出 → 支出，收入 → 收入 |
| 跳过 | 「不计收支」或中性交易（信用卡还款、余额宝 / 零钱通转入转出、充值提现等）、交易关闭、金额为 0 的记录 |
| 退款 | 能在同一文件中找到原交易的，从原交易金额中扣除（全额退款则整笔跳过）；找不到原交易的（原交易在更早的账单里），记为收入「其他」，备注带「退款」，可以取消勾选 |
| 金额 | 按字符串解析为「分」，不经过浮点运算 |
| 时间 | 按账单中的交易时间（北京时间）记录 |
| 备注 | `交易对方 · 商品说明`，最多 50 字 |
| 分类 | 先匹配用户规则，再匹配内置关键词规则（如美团、饿了么 → 餐饮；滴滴、地铁 → 交通），都没匹配上归「其他」 |
| 用户规则 | 在预览中把某个交易对方改成某个分类时，自动保存为规则，下次导入直接生效；规则随账号同步 |
| 已导入记录 | 和手动记的账一样可以编辑、删除。删除后再次导入同一份账单默认不恢复，可在预览的「之前删除过的记录」中勾选恢复 |

#### 2.3 隐私

- 账单文件**只在本机浏览器里解析**，不上传原始文件。只有解析后的流水像手动记账一样同步到云端。
- 用于开发的真实账单样本放在项目 `samples/` 目录，已加入 `.gitignore`，不会提交。测试用的是脱敏后自造的数据。

#### 2.4 权限

- 新增权限 `bill.import`（导入账单），前置权限为「记账」。
- 管理员自动拥有；迁移时给预置的「普通成员」角色加上这项；自定义角色由管理员按需勾选。

### 3. 架构

```
选择文件 → 读取字节 → 识别编码（UTF-8 / GBK）与格式（CSV / XLSX）
        → 识别来源（按表头特征）→ 解析为标准行 BillRow
        → 映射为 Transaction（固定 id、类型、金额、分类、备注）
        → 与本地已有 id 比对 → 预览 → 一个事务写入（标记待同步）→ syncNow()
```

- 解析逻辑放在 `src/import/`，是纯函数，可以单独测试。
- XLSX 解析按需加载，不影响首屏体积。
- 用户分类规则作为新的同步实体 `rules`；服务端同步接口新增该实体，写入需要 `bill.import` 或 `category.manage` 权限。

## 第六部分：v1.4 统计下钻、账单详情、二级分类

### 1. 背景（用户反馈）

1. 统计页点击分类后无法进入对应的明细列表。
2. 明细详情太简单，希望参照微信支付的账单详情。
3. 分类太粗，例如保险没有单独拆出来。

### 2. 需求

#### 2.1 统计下钻（P0）

- 点击统计页的分类排行项 → 进入「筛选明细」页：当月、该分类（含子分类）的全部流水，按日分组，顶部显示合计与笔数。
- 一级分类下有子分类时，筛选页顶部显示子分类分布（金额、占比），点击子分类进一步筛选。
- 统计页的环形图扇区、每日柱状图同样可以点击：扇区 → 该分类；柱子 → 当天的明细。
- 统计页新增「子分类」视图切换：按一级分类汇总（默认），或按子分类展开。

#### 2.2 账单详情（P0）

- 点击任一流水先进入**详情页**，再从详情进入编辑（之前是直接进入编辑）。没有记账权限的用户也能查看详情。
- 详情页参照微信支付的账单详情：

```
        [分类图标]
        交通 · 充电
        -19.99
     （已退款 ¥30.01）

交易对方     新电途
商品         充电预付款
支付方式     示例银行储蓄卡(0001)
交易单号     4200…0002            [复制]
商户单号     M1002                [复制]
账单来源     微信支付（导入）
```

- **已经导入过的记录**：重新导入同一份账单时，自动补全这些字段，不产生新记录。

#### 2.3 二级分类（P0）

- 分类支持两级：一级分类下可有若干子分类；流水可以记到一级分类，也可以记到子分类。
- 预置分类调整：

| 一级分类 | 子分类 |

| 交通 | 打车、地铁公交、火车飞机、加油、充电、停车过路、养车维修 |
| 购物 | 日用百货、数码电器、服饰鞋包、美妆个护、家居家装 |
| 居住 | 房租房贷、物业、水电燃气、宽带 |
| 通讯 | 话费流量 |
| 娱乐 | 电影演出、游戏、会员订阅、运动健身、旅行 |
| 医疗 | 看病、买药、体检 |
| 学习 | 书籍、课程、考试 |
| 人情 | 红包、转账、礼物、请客 |
| **保险（新增）** | 意外险、医疗险、车险、寿险 |
| **宠物（新增）** | 宠物用品、宠物医疗 |
| **美容美发（新增）** | — |
| 其他 | — |
| 收入：工资、奖金、理财、红包、**退款（新增）**、其他 | — |

- 已有用户：新的预置分类自动补齐（不覆盖已改名的分类，不改动已有流水）。
- 记账页：先选一级分类，有子分类时在下方出现子分类，可选可不选。
- 分类管理：按一级分类分组显示子分类；新增分类时可以选择上级分类；排序在同级之间进行。
- 统计：默认按一级分类汇总（子分类的金额计入父分类）。
- 导入：分类匹配到子分类，例如支付宝「保险」→ 保险，商品含「意外」→ 意外险；微信「新电途」→ 交通 › 充电。
- 已导入记录的细化：重新导入时，如果某条记录当前分类是自动分出来的一级分类或「其他」，并且新规则能分到同一个一级分类下的子分类（或从「其他」分到具体分类），就自动细化；用户手动改过的分类不覆盖（依据导入时记录的自动分类）。

### 3. 架构影响

- **不需要改服务端、不需要数据库迁移**：子分类用 `Category.parentId`，导入原始字段放在 `Transaction.meta`，都随同步的 JSON 存储。
- 新增页面：`#/tx/:id`（详情）、`#/list`（筛选明细，参数 `month`、`type`、`category`、`day`）。

## 第七部分：v1.5 明细的搜索、筛选与排序

### 1. 背景

导入账单之后流水数量明显增多，只能按月份翻看，不方便查找特定的交易、做专项统计。

### 2. 需求

- **入口**：明细首页右上角「搜索 / 筛选」；统计页下钻、筛选明细页也是同一个页面（「查询明细」页）。
- **关键词搜索**：在备注、交易对方、商品、分类名中查找，不区分大小写。
- **筛选条件**（可组合）：

| 条件 | 选项 |
|---|---|
| 时间 | 本月（默认）、上月、近 3 个月、今年、全部、自定义起止日期 |
| 收支 | 全部、支出、收入 |
| 分类 | 多选；选一级分类时自动包含其子分类 |
| 金额 | 最小 ~ 最大（元），可只填一边 |
| 来源 | 手动记账、支付宝导入、微信导入（多选） |

- **排序**：时间从新到旧（默认）、时间从旧到新、金额从高到低、金额从低到高。
  - 按时间排序时按天分组显示；按金额排序时平铺显示，每行带日期。
- **结果汇总**：顶部显示支出合计、收入合计、笔数；只选了一个一级分类时，保留 v1.4 的子分类分布。
- **已生效条件**：以标签形式显示在列表上方，可以单独移除，也可以一键重置。
- **状态保留**：所有条件写在网址参数里，从详情页返回、刷新页面后条件不丢失。
- **编辑交易对方 / 商品**（用户追加）：编辑页可以修改交易对方和商品，导入记录自动带出原值，手动记账也可以填写；保存时保留导入的其他原始字段（状态、单号等）。如果备注仍是导入时自动生成的「交易对方 · 商品」，跟随一起更新。

### 3. 架构影响

- 纯前端功能，数据仍从本机 IndexedDB 读取，不需要改服务端、不需要迁移。
- 筛选与排序逻辑放在 `src/services/txFilter.ts`（纯函数，可单元测试）。
