### 2.1 支付宝（`支付宝交易明细(起-止).csv`）

| 项 | 实际情况 |
|---|---|
| 编码 | **GBK**（无 BOM） |
| 结构 | 约 23 行说明（含姓名、账号、汇总数据），然后是表头，之后全部是数据，没有结尾说明 |

| 收/支 | `支出`、`收入`、`不计收支` |
| 交易状态 | 样本中有 `交易成功`、`支付成功`、`等待确认收货`、`还款成功`；另外已知还有 `交易关闭`、`退款成功` |
| 交易订单号 | 28–32 位数字，**末尾带 `\t`** |
| 特殊记录 | 金额为 `0.00` 的支付成功记录（全额抵扣）；信用卡还款为「不计收支 / 还款成功」 |
| 交易分类 | 有，例如 餐饮美食、日用百货、数码电器、家居家装、宠物、医疗健康、美容美发、保险、爱车养车、信用借还 |

| 项 | 实际情况 |
|---|---|
| 格式 | **XLSX**，单个工作表，文字为共享字符串，时间和金额为数字单元格 |
| 结构 | 约 15 行说明（含昵称、汇总），然后是表头和数据 |
| 表头 | `交易时间, 交易类型, 交易对方, 商品, 收/支, 金额(元), 支付方式, 当前状态, 交易单号, 商户单号, 备注` |
| 交易时间 | **Excel 日期序列数**，例如 `46322.3872916…`，按 UTC+8 解读 |

| 收/支 | `支出`、`收入`；中性交易为 `/` |
| 当前状态 | `支付成功`、`已转账`、`对方已收钱`、`已存入零钱`、`已全额退款`、`已退款(¥30.01)`、`已退款¥30.01` |
| 交易类型 | `商户消费`、`扫二维码付款`、`转账`、`微信红包`、`<商户名>-退款` 等 |
| 交易单号 | 28–32 位，文件内不重复 |
| 退款 | **原交易与退款是两行**：原交易「支出 50，状态 已退款(¥30.01)」，退款行「交易类型 新电途-退款，收入 30.01，状态 已退款¥30.01」。两行的交易单号不同，退款行的商户单号为空 |

## 3. 读取与识别

| 步骤 | 规则 |
|---|---|
| 格式 | `.xlsx`（文件开头是 ZIP 头 `PK`）→ XLSX；否则按 CSV 文本处理 |
| 编码（CSV） | 先按 UTF-8 严格解码（去掉 BOM），失败则按 GBK 解码 |
| 表头 | 找第一行同时含「交易时间」「收/支」的行；表头单元格去掉首尾空白，末尾的空列忽略 |
| 来源 | 表头含「交易订单号」→ 支付宝；表头含「交易单号」和「当前状态」→ 微信；否则报「无法识别的账单文件」 |
| 必需列 | 支付宝：交易时间、收/支、金额、交易状态、交易订单号；微信：交易时间、收/支、金额(元)、当前状态、交易单号。缺少任何一列都报错并指出列名 |
| 单元格 | 去掉首尾空白与 `\t`；`/` 视为空 |
| 时间 | 支付宝按 `YYYY-MM-DD HH:mm:ss` 解析为北京时间；微信序列数换算：`(序列数 − 25569) × 86400000 − 8 小时`，按秒四舍五入 |
| 金额 | 去掉 `¥`、`,`；字符串按「分」精确解析；数字单元格出现多于两位的小数时（浮点表示）四舍五入到分 |

## 4. 标准行与流水映射

```ts
interface BillRow {
  source: 'alipay' | 'wechat';
  orderNo: string;
  time: number;
  direction: 'expense' | 'income' | 'neutral';
  amountFen: number;          // 账单原始金额
  netFen: number;             // 扣除退款后的金额（见 §5.2）
  counterparty: string;
  goods: string;
  txType: string;             // 微信「交易类型」；支付宝为空
  billCategory: string;       // 支付宝「交易分类」；微信为空
  status: string;
  refundOf?: 'matched' | 'unmatched';   // 仅退款行
}
```

映射为 `Transaction`：

```
id            = `${source}-${orderNo}`
type          = direction === 'income' ? 'income' : 'expense'
amount        = netFen
occurredAt    = time
categoryId    = classify(row)                       // §6
note          = 交易对方 · 商品（去重、去掉「/」，最多 50 字）；退款行前面加「退款 · 」
source        = 'alipay' | 'wechat'
sourceOrderNo = orderNo
importedAmount = netFen                              // 用于判断导入后用户是否改过金额
```

`source`、`sourceOrderNo`、`importedAmount` 是流水的新可选字段，随记录一起同步，不需要改云端表结构。

## 5. 去重（三层）

### 5.1 第一层：交易单号（精确去重）

- 用固定 id `来源-交易单号`。同一份账单导两次、两份账单时间重叠、在另一台设备上再导一次，都会命中同一个 id。
- 检查范围包括本地**已删除**的记录：用户删掉的导入记录，重新导入时**默认不恢复**；预览中单独列为「之前删除过的记录」，可以「全部恢复」或逐条勾选恢复（v1.4.1）。

### 5.2 第二层：退款冲抵（微信）

一笔支付发生退款后，按「实际花掉的钱」记账：

| 原交易状态 | 处理 |
|---|---|
| `已全额退款` | 净额为 0，跳过（原因：已全额退款） |
| `已退款(¥X)` 或 `已退款¥X` | 净额 = 金额 − X；备注加「（已退款 ¥X）」 |

退款行（交易类型以 `-退款` 结尾，收入）的配对规则：在同一文件中，找一条**尚未被配对**的原交易，要求「原交易时间早于退款行」，并且满足下列之一：
- 原交易状态里的退款金额等于退款行金额；
- 原交易为 `已全额退款`，且原交易金额等于退款行金额。

| 配对结果 | 处理 |
|---|---|
| 配对成功 | 跳过（原因：退款已从原交易中扣除） |
| 配对失败（原交易在更早的账单里） | 导入为收入，分类「其他」，备注「退款 · …」；预览中单独列出，可以取消勾选 |

支付宝：`交易关闭` 跳过；`退款成功` 且收/支为收入的，按「配对失败的退款」处理；为「不计收支」的跳过。（支付宝部分退款在样本中没有出现，暂按此处理，以后遇到再补充。）

### 5.3 第三层：重复导入时金额有变化

上个月导入时原交易还是「支付成功」，后来发生了退款，重新导出时状态变成「已退款」，净额也就变了：

| 本地已存在该 id | 处理 |
|---|---|
| 已删除 | 列为「之前删除过的记录」，默认不恢复；勾选后按账单重新写入（`deleted` 清除，`updatedAt` 取当前时间，同步后覆盖云端的删除标记） |
| 净额与 `importedAmount` 相同 | 跳过（已导入过） |
| 净额变了，且用户没改过金额（`amount === importedAmount`） | **更新**金额与 `importedAmount`；新净额为 0 时标记删除。预览中列为「金额更新」 |
| 净额变了，但用户改过金额 | 跳过（已导入，金额已手动修改） |

### 5.4 第四层：疑似与手动记录重复

导入之前你可能已经手动记过同一笔。对每条待新增的记录，在本地查找满足以下全部条件的**手动**记录（没有 `source` 字段）：
- 收支类型相同、金额相同；
- 时间相差不超过 30 分钟；
- 这条手动记录还没被本次导入中的其他记录匹配过。

找到的标为「疑似重复」，**默认不导入**，预览中显示对应的手动记录，可以逐条勾选「仍然导入」。

## 6. 分类（`classify.ts`）

优先级：用户规则 → 账单自带分类（支付宝）→ 内置关键词 → 「其他」。收入类记录只在收入分类中选择。

### 6.1 用户规则（同步实体 `rules`）

```ts
interface Rule { id: string; keyword: string; categoryId: string; updatedAt: number; dirty?: 0 | 1 }
```

- 匹配对象：交易对方 + 商品说明，包含即命中，不区分大小写；关键词越长越优先。
- 在预览中把某个交易对方的分类改掉时，自动保存规则（`keyword` = 交易对方，`id` = `rule-` + 关键词的哈希，同一关键词只保留一条）。
